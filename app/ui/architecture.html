Source Systems

  • Ledgerline CRM — households, contacts, relationships, risk profiles, soft deletes. REST API with cursor pagination, 429/503 errors, one-second timestamp precision.
  • Meridian Custody — accounts, positions, balances via CSV file drops. Each drop has a manifest with SHA-256 hashes, row counts, and a supersedes chain for corrections.

Design Principles

  • Source-agnostic canonical model — Pravar-owned UUIDs, never source IDs as PKs.
  • Policy-first — every sensitive field controlled by data_policy.yaml, not route handlers.
  • No silent correction — source anomalies are surfaced as findings, not silently fixed.
  • Idempotent everywhere — replaying a sync or re-ingesting a drop is always safe.

Identity Rules

  • Canonical IDs — hh_, per_, acc_ prefixed UUID4s. Source IDs are stored as attributes only.
  • Account normalisation — strip spaces/hyphens, require 8 digits, format as NNNN-NNNN.
  • No auto-merge — duplicate persons are flagged, not merged.

PII Storage

  • tax_id → HMAC-SHA256 keyed hash. Never stored raw.
  • email, phone, dob, notes → Fernet symmetric encryption. Decrypted only at egress.
  • primary_tax_id from CSV → read, immediately discarded. Never reaches ORM.
  • Notes: redact_free_text() applied before encrypting.

Monetary Values

  • All amounts stored as exact Decimal strings in SQLite Text columns.
  • _parse_decimal() strips $ and commas before conversion.
  • Totals computed with Decimal — never float.
  • Currency always explicit ISO 4217 (USD).

Cash Double-Count Guard

The custodian reports cash twice: as a CASH asset-class position AND in cash_balance on the Valuation row. The reconciliation check uses:

computed_total = Σ(non-CASH positions) + valuation.cash_balance
discrepancy = |computed_total − valuation.total_market_value|

This avoids inflating the reconciliation baseline by counting cash twice.

7 Key Engineering Trade-offs

Each decision made for correctness at assignment scope. Documented for interview defence.

Inclusive updated_since + idempotent upserts
CRM timestamps have 1-second precision; multiple records can share the same timestamp. An exclusive window (checkpoint + 1s) would silently skip tied records.
✓ Chosen: inclusive boundary, replay the exact boundary timestamp safely via upsert.
Supersedes chain, not delivery timestamp
Custodian folders can be delivered out of order. A correction arriving 3 days late should override the original, regardless of which folder was processed last.
✓ Chosen: manifest supersedes field is authoritative; delivery time is metadata only.
Retain duplicate persons, never auto-merge
Robert Chen / Bob Chen: a wrong merge produces wrong financial advice. The cost of a missed merge is a finding; the cost of a wrong merge is incorrect AUM for an AI agent.
✓ Chosen: retain separately, emit POSSIBLE_DUPLICATE_PERSON, require human resolution.
HMAC for tax IDs, Fernet for other PII
Tax ID needs to support matching (same HMAC = same person) but must never be recoverable. Email/phone/DOB need to be presented to ops in plain form.
✓ Chosen: keyed HMAC (non-reversible) for tax_id; Fernet (reversible) for the rest.
Reconciliation failure ≠ sync failure
A bug in a reconciliation rule should not prevent canonical data from being served. Findings are operational metadata; sync data must always be available.
✓ Chosen: ReconciliationEngine errors are caught and logged; sync run remains success.
SQLite over PostgreSQL
No concurrent writers at assignment scale. WAL mode gives safe concurrent reads. PostgreSQL would add operational complexity (connection pooling, pg_dump) for no correctness benefit here.
✓ Chosen: SQLite WAL with FK enforcement. Easy to migrate: change DATABASE_URL.
Synchronous sync execution
POST /v1/ops/sync blocks until complete. For a 100k-row custodian drop a job queue would be appropriate. At assignment scale, synchronous is simpler and more debuggable.
✓ Chosen: synchronous. Noted in README as production limitation.
Policy YAML drives egress logic
Hard-coding field rules in route handlers means adding a new field requires editing multiple files. The YAML approach means a new field rule = one YAML entry.
✓ Chosen: PolicyEngine reads YAML at startup; apply_egress() looks up transform by field + principal.
